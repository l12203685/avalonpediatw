## 1. 自我對打方法

- **對局**：`SelfPlayEngine` 10 人局（刺、娜、德、奧、派、梅 + 4 忠臣，含湖中女神），agent = `HeuristicAgent`（走 ForwardAgent；湖目標與宣告走 agent 層 `pickLakeTarget` / `declareLake`，所以每個 agent 的 tuning 都生效）。
- **配對設計**：每組種子跑三局，三局的座位順序與角色完全相同（引擎的洗牌在 `(seed, 局號)` 播種的 PRNG 下進行）：
  - A：variant 坐紅方、baseline 坐藍方；
  - B：baseline 坐紅方、variant 坐藍方；
  - C：兩邊都是 baseline（配對對照）。
- **共用亂數**：每個決策在 `(seed, 局號, 座位, 階段, 回合, 提議數, 任務數, 湖數, 當前隊伍)` 播種的 PRNG 下執行（同 agreementBenchmark 的播種方式），所以同一情境下 baseline 兩邊做一樣的決定；variant 與 baseline 相同時三局完全一致（control 列合計恰為 50.0%）。
- **勝負**：引擎的最終結果 — 三紅或三藍死 = 紅勝，三藍活 = 藍勝（Edward 2026-10-12 裁定的「最終」口徑）。另列任務結算（三紅率）與刺殺結算（三藍局刺中率）。
- **指標**：
  - **紅方立場** = A 局紅勝率，對照 = C 局紅勝率；差 = 逐種子配對差（A − C）的平均與常態近似 95% 區間。
  - **藍方立場** = B 局藍勝率，對照 = C 局藍勝率；差 = B − C。
  - **合計勝率** = 逐種子 (A 紅勝 + B 藍勝) / 2 的平均（variant 一半時間當紅、一半當藍，對手都是 baseline），區間為逐種子常態近似；variant = baseline 時恰為 50%。
  - 注意不能拿 A 對 B 比：每局都是 variant 一邊、baseline 另一邊，A 的紅勝率與 B 的藍勝率加起來恆為「合計」，兩個立場的「差」會是同一個數字；所以立場要對 C。
- **局數**：每開關 5000 組種子 × 3 = 15000 局（任務要求每組至少 2000 局）；10 人局約 35 ms 一局（GameEngine 的事件 log 在跑分時關掉）。
- **自我對打的紅方極強**：baseline 自打自紅勝約 88%（三紅率約 84%），真人 10 人局紅勝約 70%、三紅約 45%。藍方立場的數字因此都很小（約 12%），差距要看配對差的區間而不是絕對值。

## 3. 刺殺選人模型

### 方法

- **資料**：`sheets_cache.json` 的 `牌譜` 經 `parseReplayGame` 嚴格重播的 1970 局 10 人局中，到達三藍且有刺殺目標的 **1048 局**。標籤 = 真正的梅林座位；輸入 = 刺客在刺殺階段的觀測（`buildReplayObservation`：公開歷史 + 刺客的 `knownEvils`（娜、德）+ 刺殺階段的完整紅方名單 `allEvilIds`，後者只用來排除候選與判斷湖主陣營）。**不讀 roleMap**。
- **切分**：以對局為單位，`fnv1a("assassin|" + 流水號) mod 100 < 70` 為訓練（731 局）、其餘測試（317 局），固定不隨機。
- **模型**：條件邏輯回歸（每局在 6 個好人候選上做 softmax：P(c = 梅林) ∝ exp(w · x_c)），39 個特徵（`src/ai/assassin/AssassinModel.ts` 的 `ASSASSIN_FEATURE_NAMES`：被提議比例、成功 / 失敗任務數、是否從未在失敗隊、隊伍含可見紅的比例、紅方隊長選到的比例、隊外白 / 隊內黑比例、對含刺客 / 含隊友隊伍的投票、對乾淨隊伍的隊外白 / 隊內黑、票與結果一致度、與刺客同票比例、隊長次數與派隊內容、被紅方 / 非紅方湖主宣告好壞、當過湖主、湖了紅方、座位 one-hot）。訓練列標準化後用全批次 Adam 最佳化負對數概似 + L2；λ 由訓練局 5 折交叉驗證（對數概似）在 {0.001…1} 選出 **λ = 0.1**；標準化折回原始尺度權重寫入 `assassinModelWeights.ts`（softmax 不需要偏置）。不引入新依賴。
- **接線**：`AgentTuning.assassinModel` 打開時 `HeuristicAgent.assassinate` 在 `allEvilIds` 過濾後改用 `pickAssassinTargetByModel`（同分依座位序）；ForwardAgent 的刺殺本來就委派給 baseline，所以兩條路徑一致。

## 5. 限制

- 自我對打的對手是機器人，紅方 88% 勝率代表機器人藍方很弱；「不變弱」是對機器人對手而言，對真人的效果要靠一致性基準與上線後的戰績（`/stats`）觀察。
- （2026-10-13 已修正）正式伺服器的機器人湖目標原本是隨機、湖宣告走 `GameServer` 自己的規則（好人說實話、紅方反說），湖的開關只影響自我對打與基準。現在 `GameServer.pickBotLakeTarget` / `decideBotLakeClaim` 先問機器人自己的 agent（`HeuristicAgent.pickLakeTarget` / `declareLake`，與自我對打相同的 `LakePolicy`），agent 不存在、沒有湖的介面、出錯或給了不合法的目標時才退回舊做法；`AVALON_BOT_LAKE_VIA_AGENT=0` 可整個退回舊做法（第 6.3 節）。
- 自我對打裡「把湖留在紅方」本身可能量不到好處：機器人好人拿湖後的宣告也會被同一條硬3 規則誤傷（誠實的好人宣某人藍、之前帶隊沒放他 → 一樣被當成可疑，這條規則連湖之前帶的隊也算），所以讓藍方少拿湖在自我對打裡不一定對藍方不利。這可能是紅方湖策略在自我對打裡變弱的原因之一，但沒有直接驗證；這是機器人對手的特性，對真人的效果要看一致性基準與上線戰績（第 6 節）。
- 刺殺模型的訓練集只有 731 局；特徵全是手寫的計數比例，沒有用到座位以外的玩家身分（故意不用名字，避免針對特定玩家）。
- 一致性基準的 ED 樣本小（刺殺 17 筆、湖宣告 14 筆），ED 專屬的結論看 Sin / top / population 比較穩。

## 6. 紅方湖中女神：盡量湖隊友（`evilLakeHumanStrategy`，2026-10-13）

### 6.2 策略（`LakePolicy.pickEvilLakeTargetHuman` / `decideEvilLakeClaimHuman`）

全部是固定規則，不用亂數（開關關閉時原本的 `Math.random` 呼叫順序完全不變）：

1. **湖誰**：有看得到的隊友可湖、而且之後還有湖（R2、R3 後的湖）→ 湖隊友。有兩位時，先選**自己帶隊時最少把他拿掉的那位**（每次都放在隊上 = 0 次；替自己沒帶的人背書是破綻），再選比較被懷疑的（宣好能洗掉最多壓力），再依座位。
2. **最後一次湖**（R4 後，被湖的人之後拿不到湖，留在紅方已沒有價值）→ 只要有一位隊友帶一點嫌疑（嫌疑分數 > 0）就湖他洗白、幫他上最後一個任務；隊友全都毫無嫌疑才改湖藍方。實際上到這時（比分 2:2）幾乎每位隊友都有一點嫌疑：真人牌局裡最後一次湖、有隊友可湖的 147 次，這條規則有 143 次還是湖隊友（真人只有 26 次，17.7%）；自我對打裡則是每次都湖隊友。所以實際行為幾乎等於「最後一次也湖隊友」，與第 1 點只差在極少數情況。
3. **湖藍方**（沒有隊友可湖，或第 2 點改湖藍方）：紅方已拿兩局、而且有藍方跟自己一起出過失敗任務 → 湖那位（最可疑的優先）並**宣紅**（嫁禍、讓資訊變混亂）；否則照第 1 點的背書順序挑藍方並**說實話宣好**（買好感）。
4. **宣告**：隊友一律宣好；湖到原本看不見的紅方（奧伯倫，或奧伯倫湖到任何紅方）宣好掩護；藍方照第 3 點。
5. **奧伯倫**看不到隊友，所以永遠走第 3 點，用的是同一個順序（紅方聽牌時先找一起出過失敗任務的人嫁禍，否則先選自己帶隊時最少拿掉的人，再看嫌疑），**不是**「挑最可疑的人」；湖到紅就宣好，湖到藍照第 3 點。這個順序找不到隱藏的紅方：真人牌局裡奧伯倫持湖的 289 次，這條規則湖到的人是紅方的只有 27.7%（80/289），比在合法目標裡亂挑（32.8%）和真人（33.6%）都低；改成單純湖最可疑的人也一樣是 27.7%（奧伯倫自己出的失敗會讓同隊的藍方背上嫌疑，可能是原因）。自我對打裡機器人奧伯倫湖到紅方的比例見 6.4。
6. **與其他開關的關係**：開關打開時取代舊的紅方湖目標規則（包含 `AVALON_EVIL_LAKE_BRING_FRIEND=0`）；宣告上若同時打開 `evilLakeClaimAlwaysGood`，以「一律宣好」為準（目標仍由本策略決定）。好人持湖完全不受影響。
7. 戰術組合可用 `AVALON_EVIL_LAKE_HUMAN_VARIANT`（例如 `chaos=never`）切換，**只有基準腳本**（`selfPlayStrength.ts`、`agreementBenchmark.ts`）會讀；伺服器不讀，設在正式環境也沒有作用。

### 6.3 線上對局

`GameServer` 的機器人湖原本是隨機選目標、紅方把看到的真相反說，湖的開關（含已採用的 `goodLakeTargetMostSuspicious`）對線上都沒有作用。現在 `pickBotLakeTarget` / `decideBotLakeClaim` 用伺服器原有的觀測建構（`buildBotObservation`）問機器人自己的 agent（`pickLakeTarget` / `declareLake`），時間安排與階段流程不變；agent 不存在、沒有湖的介面、出錯或回傳不合法的目標時，退回舊的隨機目標 / 反說規則（`GameServer.botLake.test.ts`）。

上線後的實際變化（當時 `evilLakeHumanStrategy` 預設關；同日打開後，線上紅方機器人改用 6.2 的新策略，見 6.5）：

- **機器人好人**：湖最可疑的人並說實話（原本隨機湖、說實話）。
- **機器人紅方**：改用自我對打一直在用的舊紅方規則 —— 隊友被懷疑就湖隊友洗白，否則湖最像梅林的人；隊友宣好，對手看像不像梅林決定宣好或宣紅（部分角色帶一點隨機說謊）。**不是** 6.2 的新策略。原本是隨機湖、看到什麼就反說。一致性基準上，舊紅方規則的湖宣告比反說更像真人（population 58.2% vs 45.8%）；但「舊紅方規則 vs 線上反說」的強度沒有量過（自我對打的對照組本來就是舊紅方規則）。
- **要整個退回原本的線上做法**（隨機目標、好人說實話、紅方反說）：`AVALON_BOT_LAKE_VIA_AGENT=0`。**要讓線上紅方機器人退回舊紅方規則**（不用 6.2 的新策略）：`AVALON_TUNING_EVIL_LAKE_HUMAN_STRATEGY=0`。

### 6.5 決定與待決事項

- **第一輪（2026-10-13）依規則不採用**：定案版的湖宣告更像真人（四個群都大幅提高），湖目標只到簡單規則的水準，自我對打換新種子後紅方變弱（五個種子合併 −0.6pp [−0.9pp, −0.3pp]）。
- **Edward 裁定（2026-10-13，原文）**：「1 紅方新湖法先打開 變弱應該從其他地方調整修正 (先像真人 再從策略上提高勝率)」，並問「有沒有可能勝率少是因為他本身策略就沒有進行修正?」→ `DEFAULT_AGENT_TUNING.evilLakeHumanStrategy = true`（legacy 仍關；`AVALON_TUNING_EVIL_LAKE_HUMAN_STRATEGY=0` 可關掉），變弱的原因與從其他紅方決策補回的做法見第 7 節。這是依擁有者裁定、不是依強度規則採用：先像真人。
- **當時列給 Edward 的待決事項**（第 1 點已由上面的裁定回答，其餘的處理見第 7 節）：
  1. 要不要接受這個幅度的變弱（約 −0.6pp，機器人對機器人）換取更像真人的湖宣告。`chaos=never`（藍方一律說實話）與定案版強度相同，宣告更貼近全體玩家與 ED（population 77.2%、ED 85.7%），但機器人就完全不嫁禍（0%），也不像真人；定案版則嫁禍得比真人多很多（6.4 表）。
  2. 真人在有隊友可湖時只有約 24% 去湖隊友（接近亂湖），最後一次湖只有 18%；新策略幾乎每次都湖隊友。這是依裁定的規範做法，不是牌譜多數。若要更像真人，可以收緊最後一次湖的條件（例如隊友在失敗任務上、而且嫌疑不低於中位數才湖他），改了要重跑兩個基準。
  3. 奧伯倫的湖：目前的順序湖到紅方的比例（27.7%）比亂挑（32.8%）還低。要不要改成亂挑或其他規則，由 Edward 決定；改了要重跑。
  4. 機器人的硬3 規則連湖**之前**帶的隊也算、誠實的好人也會被標記（`lakeChainTracker.findRule3Violators`），所以自我對打可能量不到「讓藍方拿不到湖」的好處（第 5 節）。要不要讓硬3 只看湖之後的隊伍，會改變所有好人機器人的判斷、需要另外重跑全部基準，這次沒有動。
  5. 線上機器人湖改由 agent 決定（6.3）：好人改湖最可疑的人、紅方改用舊紅方規則，強度沒有和原本的線上做法比過；不想要可用 `AVALON_BOT_LAKE_VIA_AGENT=0` 退回。
